# Performance baseline

The reference numbers for the Windows port: the same machine, the same logs, the same benchmarks.
A Windows build should land close to these. Where it is clearly slower, the platform layer (file
mapping, RAM-backed cache, prefetch, threads) is the first suspect. Measured 2026-10-03.

## Machine

| | |
|---|---|
| CPU | Intel Core i7-12700K (8 P + 4 E cores, 20 threads) |
| RAM | 32 GB (31 GB usable) |
| Disk | Kingston NV1 1 TB NVMe (SNVS1000G, QLC): `dd` sequential read 1.0 GB/s, sustained write 285 MB/s once its SLC cache is full |
| OS | Ubuntu 24.04, Linux 7.0.0-38 |
| Compiler | GCC 13.3, default build type (RelWithDebInfo), no sanitizers |

The QLC disk makes cold runs noisy. After several GB of writes, both its writes and its reads slow
down for a while. Take cold numbers from a rested disk and repeat them.

## Test logs

Generated by `examples/tentacle_sim.py` (deterministic: the same size gives the same file):

```bash
examples/tentacle_sim.py --file g2.log  --size 2G    # 45 691 141 frames, 9 ids, candump
examples/tentacle_sim.py --file big12.log --size 12G # 274 146 849 frames
```

Cold means the source log is not in the page cache. On Linux this is done with
`posix_fadvise(POSIX_FADV_DONTNEED)` on the file. On Windows, reboot, or use RAMMap's
"Empty Standby List".

## Commands

The benchmarks are doctest cases that do nothing unless their environment variables are set. Point
`XDG_CACHE_HOME` (on Windows: the cache directory) at an empty directory so the first load really
parses.

```bash
# Replay: load as the Replay window does, then play "as fast as possible" (twice: new, cached)
XDG_CACHE_HOME=/tmp/kcache KRAKEN_BENCH_FILE=g2.log build/tests/replay/replay_test -tc="replay bench"
# Frame cache: build, open, 1000 random jumps, decode one id over the whole file
XDG_CACHE_HOME=/tmp/kcache KRAKEN_BENCH_FILE=g2.log build/tests/frame_cache/frame_cache_test -tc="frame cache bench"
# Conversion to every format (output directory should be a RAM disk, or the disk's write speed is measured)
XDG_CACHE_HOME=/tmp/kcache KRAKEN_BENCH_FILE=g2.log KRAKEN_BENCH_OUT=/dev/shm/kconv build/tests/convert/convert_test -tc="convert bench"
```

## Replay (the main target)

| | 2 GB (45.7M frames) | 12 GB (274M frames) |
|---|---|---|
| First load, log already in RAM | **0.92 s** (2.2 GB/s) | - |
| First load, log from disk | 3.9 s (disk bound, about 0.5–1 GB/s) | **22.4 s** (best run 16.2 s; disk reads it in 12.6 s) |
| Cache saved to disk (in the background, after the log is shown) | +0.4 s | +19 s |
| Open again (cache mapped) | **0.03 ms** | **0.03 ms** |
| Play "as fast as possible" into the trace | **1.0–1.1 s = 41–45M frames/s** | **6.1–7.4 s = 37–45M frames/s** |
| Jump: seek a time + 50 rows with Δt, per jump | 13 µs | 31 µs |
| Decode one id over the whole file (graph, zoomed out) | 1.38M frames in 34 ms | 8.3M frames in 244 ms |
| Cache size | 1.57 GB | 9.4 GB |
| Peak RSS during first load (mostly mapped file pages) | 3.0 GB | 17.9 GB |

In the GUI (8 GB log, 182 764 569 frames, cache rebuilt from disk), the Replay window showed
"loaded in 16 s".

How the first load gets there (`src/ui/frame_cache.cpp`):
- The source is mmap'ed and parsed in 1 MB blocks on up to 16 threads, in a sliding window.
- Each worker encodes 32-byte records and copies them straight into the output mapping.
- One thread reads the file ahead in 16 MB `pread`s, skipping chunks that `mincore` reports as already resident.
- With enough free RAM the cache is built in a memfd and saved in the background.
- The per-id index (pass 2) is built in parallel slices.

## Conversion (secondary)

2 GB candump, input already cached, output on tmpfs:

| Format | Time | Output |
|---|---|---|
| candump | 1.6–1.8 s | 2.0 GB |
| ASC | 2.6–2.8 s | 4.4 GB |
| MF4 | 1.7–1.9 s | 3.4 GB |
| pcap | 1.3 s | 1.4 GB |
| pcapng | 1.9–2.0 s | 2.1 GB |
| TRC | 2.3–2.4 s | 3.2 GB |
| BLF | 2.1–2.2 s | 2.1 GB |

Each format is encoded in parallel chunks of 64k frames on up to 16 threads and written in order.

## Windows (2026-10-03)

Same machine, Windows 11, MinGW-w64 GCC 16.2, RelWithDebInfo. Not a clean comparison: WSL2 was
running and holds part of the 32 GB, and the output went to the QLC disk (no RAM disk), after
about 45 GB had been written to it.

| | 2 GB (45.7M frames) | 16 GB (365.5M frames) | Linux, 2 GB |
|---|---|---|---|
| First load, log already in RAM | 1.33–1.35 s | - | 0.92 s |
| First load, log partly in RAM | - | 13.9 s (replay), 22.9 s (frame cache bench, 716 MB/s) | - |
| Open again (cache mapped) | 1–7 ms | 4.6–7 ms | 0.03 ms |
| Play "as fast as possible" into the trace | 2.4–3.3 s = **14–19M frames/s** | 16.8–18.7 s = 19.5–21.8M frames/s | 41–45M frames/s |
| Jump: seek a time + 50 rows with Δt | 34 µs | 70 µs | 13 µs |
| Decode one id over the whole file | 1.38M frames in 333 ms | 11.1M frames in 2.45 s | 34 ms |
| Cache size | 1.57 GB | 12.5 GB | 1.57 GB |

Peak RSS is not reported on Windows (-1). With the cache evicted from RAM (after the 16 GB run)
the same 2 GB decode took 76 s and a jump 42 ms: random reads of the mapping from the disk.

Conversion of the 2 GB log to disk, best run per format: candump 3.8 s, MF4 3.0 s, pcap 1.4 s,
pcapng 2.2 s, BLF 4.3 s, TRC 12 s, ASC 67 s. Repeated runs of one format differed by up to 30x
(candump 3.8–111 s, pcapng 2.2–14 s, TRC 12–32 s): this measures the disk, not the code. Measure
again with the output on a RAM disk before drawing conclusions.

## What to watch on Windows

- **File mapping and the RAM-backed build:** `CreateFileMapping` + `MapViewOfFile`, with a
  pagefile-backed section in place of memfd. A first load much slower than the Linux numbers with
  the log already in RAM points here.
- **Prefetch:** `ReadFile` in 16 MB chunks on one thread; residency check via
  `QueryWorkingSetEx` or simply always reading. Cold loads should still be disk bound.
- **Thread start-up cost:** `std::async` starts a thread per 1 MB block (2048 per 2 GB). Thread
  creation is slower on Windows; a persistent pool is the upgrade if the warm load lags.
- **Antivirus:** Defender scanning the 1.5–9 GB cache file on every open. Exclude the cache
  directory before measuring.
